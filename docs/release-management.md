# Release Management — workflows, examples, and schemas

This article documents a practical release workflow using Git branches, CI, and infrastructure. It includes concrete commands, examples and a JSON schema for release metadata suitable for automation.

## Branch types

- `master` — production code, deployments are driven by tags on this branch.
- `develop` — integration branch for ongoing work.
- `release/*` — short-lived stabilization branches for an upcoming release.
- `future/*` — branches used to collect large epic work; integrate often.
- `hotfix/*` — urgent fixes created from `master`.

## Recommended release workflow (example)

1. Create a release branch from `develop` when feature-complete:

```pwsh
git checkout develop
git pull origin develop
git checkout -b release/1.2.0
```

2. Stabilize: fixes, docs, bump version, update changelog.

3. Run full CI and deploy to staging for QA. Example: GitHub Actions job `release-staging`.

4. After QA sign-off, merge to `master`, tag and push the tag. Use annotated tags:

```pwsh
git checkout master
git pull origin master
git merge --no-ff release/1.2.0 -m "Merge release 1.2.0"
git tag -a v1.2.0 -m "Release v1.2.0"
git push origin master --follow-tags
```

5. Merge the release back into `develop` to keep fixes:

```pwsh
git checkout develop
git merge --no-ff release/1.2.0 -m "Merge release 1.2.0 back into develop"
git push origin develop
```

6. Delete the release branch (optional):

```pwsh
git branch -d release/1.2.0
git push origin --delete release/1.2.0
```

## Hotfix flow

For production issues:

```pwsh
git checkout master
git pull origin master
git checkout -b hotfix/1.2.1
# apply fix, commit
git commit -am "fix: critical bug"
git checkout master
git merge --no-ff hotfix/1.2.1
git tag -a v1.2.1 -m "Hotfix v1.2.1"
git push origin master --follow-tags
git checkout develop
git merge --no-ff hotfix/1.2.1
git push origin develop
```

## CI / Infrastructure mapping

- `release/*` → `staging`/`preprod` environment (full regression tests + manual QA).
- `master` tags (`v*`) → production deployment pipeline (artifact promotion).
- `future/*` → test/feature environments; use feature flags for unfinished features.

Automate artifact storage (Docker image registry, npm packages, etc.) and make production deployments trigger only on release tags.

## Release metadata schema

Provide a small JSON Schema that CI and release tooling can use to validate release metadata (changelog, artifacts, owner, etc.).

File: `schemas/release-metadata.schema.json`

Example of common fields: `version`, `date`, `releasedBy`, `artifacts`, `notes`.

Use this schema in pipelines to validate a `release.json` file generated by release tooling or maintained by the release manager.

---

Example `release.json` (matches the schema):

```json
{
  "version": "1.2.0",
  "date": "2025-12-20T12:00:00Z",
  "releasedBy": "alice",
  "artifacts": [
    { "type": "docker", "name": "myapp", "tag": "1.2.0", "uri": "ghcr.io/myorg/myapp:1.2.0" }
  ],
  "notes": "Release contains bugfixes and performance improvements.",
  "changelog": [
    { "type": "fix", "summary": "Fix issue with login" },
    { "type": "perf", "summary": "Improve cache hit rate" }
  ]
}
```

## Examples & templates

- Changelog snippet generation: use `git log --pretty=format:'- %s' release/1.1.0..release/1.2.0`
- Release PR template: include checklist (CI green, staging validated, notes written).

## Automation ideas

- Tag-triggered CI job that promotes artifacts from staging to production only when a `v*` tag is pushed.
- A small `release.json` generated from a CI job or filled in by the release manager and validated against `schemas/release-metadata.schema.json`.
